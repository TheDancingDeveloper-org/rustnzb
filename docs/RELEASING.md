# Releasing rustnzb

GitHub is the release authority for rustnzb. Release tags use the `vX.Y.Z`
format and must point to a commit reachable from `main`.

## Release channels

The container image is published to GHCR (`…/rustnzbd`) on three tag channels:

- **`:latest`** — the current stable release. Moved only by a stable
  `vX.Y.Z` release.
- **`:beta`** — the newest pre-release, for soak testing before a stable
  promotion. A pre-release tag **never** moves `:latest`.
- **`:vX.Y.Z`** / **`:vX.Y.Z-beta.N`** — immutable, one per tag.

Pre-release tags use a suffix: `vX.Y.Z-beta.N` (also `-rc.N` / `-alpha.N`).
They are flagged as GitHub pre-releases and publish only `:vX.Y.Z-beta.N` and
`:beta`. Cutting a pre-release tag is how a build enters soak testing.

## Beta soak and promotion

Prefer shipping a stable release only after a pre-release has soaked:

1. Tag a pre-release on a `main` commit, e.g. `v1.5.0-beta.1`, and push it.
   The release workflow publishes `:v1.5.0-beta.1` + `:beta` and a GitHub
   pre-release. `:latest` is untouched.
2. Let it soak. Bump the suffix (`-beta.2`, …) for fixes during soak.
3. When satisfied, run the **Promote pre-release to stable** workflow
   (`workflow_dispatch`) with the soaked tag. It copies the **exact image
   digest** that soaked to `:v1.5.0` + `:latest`, then rebuilds the standalone
   release binaries from the same commit and publishes the stable GitHub
   release.

Because promotion copies the soaked image by digest, `:v1.5.0` is byte-identical
to the beta that was tested; only the tag changes. The image's own embedded
build ref therefore still reads the pre-release version it was built as — that
is the promoted lineage, not a rebuild. The standalone binaries are rebuilt and
carry the stable version.

A stable `vX.Y.Z` tag pushed directly (a hotfix without soak) still works and
takes the rebuild path below.

## Release checklist

1. Update `[workspace.package] version` in `Cargo.toml`. That is the single
   source for the version. `desktop/package.json`, `desktop/package-lock.json`,
   `desktop/src-tauri/Cargo.toml` and `desktop/src-tauri/Cargo.lock` must carry
   the same number, and `ci/check-version.sh` fails the release if they do not.
   The installer takes its version from the release tag at build time.
2. In [CHANGELOG.md](../CHANGELOG.md), move the `[Unreleased]` entries under
   a new `## [X.Y.Z] - YYYY-MM-DD` heading, and add its compare link at the
   bottom. Entries follow the conventional-commit subjects since the last
   tag: `feat` under Added, `fix` under Fixed, `perf` under Performance,
   `docs` under Documentation.
3. Run the checks in [DEVELOPMENT.md](DEVELOPMENT.md).
4. Merge the release change to `main` through a reviewed pull request.
5. Create and push an annotated `vX.Y.Z` tag on that `main` commit.
6. Monitor the GitHub Actions release workflow.
7. Verify the GitHub release assets, checksums, signatures, and
   multi-architecture GHCR image. The image is signed keyless with the release
   workflow's OIDC identity, and the image index carries build provenance and
   an SBOM as attestations. `SHA256SUMS-<tag>.txt` has a `.sig` and `.pem`
   alongside it:

   ```text
   cosign verify-blob --signature SHA256SUMS-vX.Y.Z.sig \
     --certificate SHA256SUMS-vX.Y.Z.pem SHA256SUMS-vX.Y.Z.txt
   cosign verify ghcr.io/thedancingdeveloper-org/rustnzbd:vX.Y.Z \
     --certificate-identity-regexp '^https://github.com/TheDancingDeveloper-org/rustnzb/' \
     --certificate-oidc-issuer https://token.actions.githubusercontent.com
   ```

   Each binary package (the two tarballs, the two `.deb` files, the two
   AppImages and the Windows installer) carries a build-provenance attestation and an SPDX SBOM
   attestation, generated by syft from the shipped file. Verify one with the
   GitHub CLI:

   ```text
   gh attestation verify rustnzb-vX.Y.Z-linux-x86_64.tar.gz \
     --repo TheDancingDeveloper-org/rustnzb
   gh attestation verify rustnzb-vX.Y.Z-linux-x86_64.tar.gz \
     --repo TheDancingDeveloper-org/rustnzb --predicate-type https://spdx.dev/Document
   ```

   The image is published under these tags:

   ```text
   ghcr.io/thedancingdeveloper-org/rustnzbd:vX.Y.Z
   ghcr.io/thedancingdeveloper-org/rustnzbd:latest
   ```

8. Refresh the package-manager manifests for the new release, then submit
   them yourself. CI renders the Windows manifests but publishes nothing.

   ```bash
   packaging/homebrew/update-formula.sh vX.Y.Z
   packaging/distribution/render-windows-manifests.sh vX.Y.Z --release-date YYYY-MM-DD
   ```

   Both scripts read the release's own `SHA256SUMS-<tag>.txt` and abort on a
   mismatch. Commit the refreshed files and follow
   [packaging/README.md](../packaging/README.md) for submission. Pre-release
   tags are never offered to package managers.

GitHub generates release notes from the tagged history, unless the tag has a
checked-in `docs/releases/<tag>.md`; that file is then used verbatim as the
release body. Review the notes before publishing.

## AppImage and macOS dmg

Both workflows wrap the Linux tarballs' binaries in
`rustnzb-<tag>-{x86_64,aarch64}.AppImage` with
`packaging/appimage/build-appimage.sh`, after the tarballs are verified and
before `SHA256SUMS-<tag>.txt` is signed, so the checksum file, SBOMs and
attestations cover them. The script needs `mksquashfs` (squashfs-tools) on the
publish runner and pins the AppImage type2 runtime by SHA-256. The AppImages
are not GPG-signed.

The macOS dmg is a dry run and off by default. The `macos-dmg` job in
`release.yml` runs only when the repository variable `RUSTNZB_MACOS_DMG` is
`true` and a `[self-hosted, macos]` runner is online. It builds the binary on
that runner (without cargo-auditable, whose pinned build is Linux-only), wraps
it with `packaging/macos/build-dmg.sh`, and uploads the dmg as a workflow
artefact. It is never attached to the release.

The dmg is **not code-signed or notarised**, by decision, so no Apple
identity or secret is involved. Gatekeeper blocks the first launch with "can't
be opened because Apple cannot check it for malicious software". Users open it
once with one of:

- Finder: Control-click `rustnzb.app` → **Open** → **Open** (on macOS 15 and
  later: try to open it, then **System Settings → Privacy & Security → Open
  Anyway**).
- Terminal: `xattr -dr com.apple.quarantine /Applications/rustnzb.app`

Check the bundle layout on any host with
`packaging/macos/build-dmg.sh vX.Y.Z --binary PATH --arch arm64 --stage-only --out DIR`.

## SBOMs and dependency accuracy

The standalone binaries are built with `cargo-auditable`, which embeds the
resolved crate list in a `.dep-v0` section of the executable. The release and
promotion workflows assert that section is present in both Linux tarballs
before generating SBOMs, so syft reads exact crate versions from the shipped
file rather than guessing from the build tree. The container image is built
the same way for the same reason.

`ci/tasks/auditable` pins the cargo-auditable version and its tarball SHA-256.
Bump both together. A binary built without the wrapper still works, but its
SBOM will list far fewer crates — the release workflow fails rather than
shipping one.

Every release asset gets a `.spdx.json` alongside it, generated by syft from
the asset itself (the Windows installer included). The container image carries
its SBOM as an image attestation instead.

### Cosign signatures on the mirrors

`SHA256SUMS-<tag>.txt` is signed keyless with the release workflow's OIDC
identity, and its `.sig`/`.pem` live on the GitHub release. The Forgejo
rollback registry and the old GHCR namespace mirror the image digest but not
the blob signature. Whether to copy the signature and certificate to those
mirrors is an open operator decision; until it is made, verify checksums
against the GitHub release.

## Standalone nzb-* crates

The crates named in `ci/nzb-crates.txt` (`mock-nntp-server` first, then
the seven `nzb-*` crates) are published to crates.io from standalone
repositories (one per crate, URL in each crate's `repository` field). This
monorepo is the head:

- **The monorepo owns version numbers.** Change a crate's `version` only in
  `crates/<name>/Cargo.toml`; the standalone repos never originate a bump.
  Keep each new version strictly above the crates.io maximum for that crate:
  a crate whose code changed since its last publish needs a new number even
  if the old one looks unreleased here. Keep every sibling requirement
  (`nzb-x = { version = "...", path = "../nzb-x" }`, and the root
  `[workspace.dependencies]`) at that sibling's current version; the
  standalone repo resolves it from crates.io, and the export refuses a stale
  one.
- **Standalone repos are sync targets.** `ci/tasks/sync-crate <name>` builds
  the standalone tree for `crates/<name>` at `HEAD` and opens a pull request
  on that crate's standalone repo. It never publishes and never pushes to the
  monorepo. `ci/tasks/sync-crate --dry-run <name>` stops before pushing and
  prints the change, including anything it would delete.
- **One export, shared by sync and drift.** `ci/crate-export.sh` defines the
  standalone tree: the crate's tracked files, with each `Cargo.toml` rewritten
  to build outside this workspace — `<dep>.workspace = true` becomes the
  `[workspace.dependencies]` entry, sibling `path = "../nzb-*"` is dropped so
  the version resolves from crates.io, and a nested member's
  `<crate> = { workspace = true }` becomes `{ path = ".." }`. A crate with
  nested crates (`crates/<name>/<dir>/Cargo.toml`, such as `nzb-decode`'s
  `ffi/`) gets a `[workspace] members = [...]` table on export, because that
  table cannot live in a member manifest here. Any other workspace inheritance
  is an error, not a silently broken manifest.
- **Publish only from a synced tag.** After a sync PR merges, publish that
  crate from a `vX.Y.Z` tag on the standalone repo — never from an out-of-sync
  tree, and never from the monorepo. Publish in the order listed in
  `ci/nzb-crates.txt`: `mock-nntp-server`, then `nzb-nntp`, `nzb-decode`,
  `nzb-core`, `nzb-news`, `nzb-postproc`, `nzb-dispatch`, `nzb-web`. The
  standalone manifests take sibling crates from crates.io, so each earlier
  crate must already be on crates.io before the next `cargo publish`.
- **Drift is gated.** The scheduled `crate-drift` job
  (`.github/workflows/quality-schedule.yml`, via `ci/tasks/crate-drift`) fails
  when any standalone repo's tree or package version differs from the export.
  A failure means a crate changed here without a sync; run
  `ci/tasks/sync-crate <name>`, merge, and publish from the tag.
- **A sync never deletes standalone-only files.** `ci/sync-preserve.txt` lists
  paths the standalone repos own: CI workflows, license, renovate, the
  per-repo agent notes (`CLAUDE.md`, `.codesight`) and `Cargo.lock`. Both the
  sync and the drift check leave those alone, unless the monorepo has started
  shipping the same path, in which case the monorepo copy wins. Each standalone
  repo resolves its own lockfile, so the sync keeps it and refreshes it with
  cargo's minimal update against the exported manifests; when that cannot
  resolve yet (a sibling version not on crates.io), the PR says so and the lock
  needs a refresh once that sibling is published. Everything else in the
  standalone tree — including `nzb-decode`'s `ffi/` and its README — must live
  in the monorepo, or the next sync will not carry it and drift will fail.
- **A sync refuses over unported work.** `sync-crate` exits 3 when a commit
  since the last sync on the standalone `main` changes a path the export does
  not carry byte-for-byte. The last sync is the newest commit whose subject
  starts with `sync` and mentions the `rustnzb monorepo` (case-insensitive;
  `sync-crate` titles its own commits and PRs `sync: <crate> from rustnzb
  monorepo <sha>`, so keep that title when squash-merging). Port the change
  into the monorepo first. A commit whose every non-preserved path already
  matches the export is treated as absorbed.
- **Overwriting standalone work is a reviewed exception.** When a standalone
  commit is superseded or already ported but still differs byte-for-byte (a
  version bump, a shim the monorepo replaced), list it in
  `ci/sync-accept.txt` as `<crate> <sha> <reason>`. `sync-crate` then goes
  ahead, prints each accepted commit with its reason, and names them in the PR
  body. Entries go stale once that sync merges and can be removed.

## Rollback

Do not move or replace a published tag. Revert the faulty change on `main`,
release a new patch version, and publish a new tag. Operators should pin an
immutable image tag rather than relying on `latest` for controlled rollouts.
